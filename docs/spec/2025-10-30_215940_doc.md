# CloudFront Request Correlation ID

## Summary
- Promote the CloudFront generated `X-Amz-Cf-Id` header to the canonical `X-Request-Id` we expose to every downstream layer.
- Ensure application code (Rails dashboard + Pegasus) and middleware can read a single correlation id for logging and telemetry.
- Emit the correlation id in structured Lograge output so CloudWatch/syslog queries can join across application/env streams.

## Background
- CloudFront already injects an opaque request identifier (`X-Amz-Cf-Id`) on every origin request. Per the platform logging inventory ([docs/logging.md](https://raw.githubusercontent.com/code-dot-org/code-dot-org/cca6477380e94f922949b7abae6d77da5c278c0f/docs/logging.md)), we currently log request metadata in: CloudFront + ALB access logs, NGINX, Rails (Lograge CEE JSON), syslog, and CloudWatch. None of these layers currently agree on a shared request id, making multi-source correlation slow.
- Rails derives its own UUID via `ActionDispatch::RequestId`, Pegasus lacks a standardized request id, and NGINX proxying drops the CloudFront header.
- Operators want to pivot on a single `x-request-id` across CloudFront → ALB → NGINX → Rails/Pegasus → background jobs, without generating or synchronizing a new id client side.

## Goals
- Use the CloudFront id as the authoritative correlation id whenever it is available.
- Backfill a generated id when requests originate outside CloudFront (local dev/tests).
- Expose the id in structured logs and response headers so clients and downstream services can chain telemetry.

## Non-Goals
- Changing CloudFront or ALB logging schema (already immutable historical data).
- Altering existing Honeybadger/New Relic ingestion (they already capture Rails `request_id`).
- Revisiting historical log files—this applies prospectively.

## Design
### HTTP Proxy Layer (NGINX)
- Forward `X-Amz-Cf-Id` upstream under both `X-Amz-Cf-Id` and `X-Request-Id` headers. All Rack apps see the CloudFront value without additional proxy configuration.
- Leaving the header blank in non-CloudFront environments is acceptable because application middleware will fall back to the framework-generated id.

### Rack Middleware
- New `Rack::CloudFrontRequestId` middleware promotes the correlation id early in the stack (runs before `ActionDispatch::RequestId` in dashboard, before any Pegasus middleware).
- Responsibilities:
  - Normalize the incoming header (`X-Amz-Cf-Id` → `X-Request-Id`).
  - Populate `env['action_dispatch.request_id']`, `env['cdo.request_id']`, and `RequestStore` for reuse during the request lifecycle/background jobs.
  - Re-emit `X-Request-Id` (and `X-Amz-Cf-Id` when present) on the response.

### Application Accessors
- Extend the shared `Rack::Request` helpers so Pegasus + Dashboard controllers can query `request.correlation_id` / `request.cloudfront_request_id` without re-parsing headers.

### Logging
- Configure Lograge custom options to merge the correlation id (and, when present, the raw CloudFront id) into each structured CEE JSON line shipped to syslog/CloudWatch. This gives operators one field to pivot on in Insights/Athena queries.
- NGINX access-log format remains unchanged for now; adding the new header to those files can follow once downstream parsing expectations are aligned.

## Rollout / Deployment
- Chef-managed NGINX templates pick up the additional proxy headers on the next cookbook deploy.
- Rack middleware + accessor changes deploy with the application code (dashboard + pegasus).
- No database or schema migrations required.

## Risks & Mitigations
- **Missing header outside CloudFront**: middleware preserves existing behavior by falling back to any inbound `X-Request-Id` or allowing the framework to generate one.
- **Header spoofing**: behavior matches existing Rack::RequestId semantics. We can add allow-lists later if needed.
- **Log consumers expecting previous schema**: new Lograge fields are additive and backwards compatible. Communicate to analytics teams before relying on them in dashboards.

## Testing Strategy
- Automated integration tests (Rails + Pegasus) assert that providing `X-Amz-Cf-Id` yields the same `X-Request-Id` in the response and that a request id is still generated when the CloudFront header is absent.
- Rack unit tests cover the new `correlation_id` helper behavior.
- (Local execution blocked in this environment because the ruby interpreter is unavailable; CI will exercise the new cases.)

## Follow-up Opportunities
- Update the NGINX `log_format` to embed the correlation id once log processing pipeline owners sign off.
- Thread the correlation id into background job instrumentation, cron logs, and Honeybadger context where we currently rely on `RequestStore`.
- Evaluate propagating the id into outbound HTTP requests so partner services can echo it back.
